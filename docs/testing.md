# Verifying a rewrite

`build.bat test` runs the **differential tests**: `rt3re_test.dll` is loaded into the real game,
replaces `WinMain` with a test runner (so the game's own C runtime is initialised but no game code
has run), and calls the original function and the rewrite on the same inputs. Results:
`difftest.log` in the game folder.

```
DIFFTEST(text_ToUpper) {
    auto orig = (int(__fastcall*)(char))0x51d660;
    for (int c = 0; c < 256; ++c)
        EXPECT_EQ(orig((char)c), rt3::ToUpper((char)c), "c=%d", c);
}
```

Every rewritten *leaf* function (one whose original calls nothing but pure C runtime functions
or other such leaves, and has no indirect call or jump; about 1,200 of them) is also tested
generically by `leaves_all` (`tests/test_leaves.cpp`, table
generated by `tools/gen_leaftests.py`): both versions get the same random objects and arguments
and must return the same, leave memory the same and write the same bytes to the game's globals
(found by write-protecting the exe's data sections during the call). It runs in a process of its
own after the other tests (results: `difftest_leaves.log`), since the originals, fed random data,
can write through the game's globals into heap objects.

Float-to-integer casts in the rewrite convert exactly like the original: `src/core/ftol.cpp`
routes the compiler's conversion helpers to the exe's own `_ftol`, which differs from ours for
values beyond 32 bits and for NaN. `python tools/ftolcheck.py` checks the build's link maps for
that.

`python tools/simcheck.py` is the end-to-end check: it loads a saved game, runs 2,000 frames,
saves, and compares every write of that save between the original game and the rewrite.
It also compares what is drawn: everything handed to Direct3D, one CRC per frame
(`src/drawtrace.cpp`). `--standalone` runs the rewrite through `OpenRT3.exe`;
`--do=@tools/actions.txt` plays scripted player actions (tools, windows, editor, dialogs);
`--off=Name,...` keeps functions original, also where rewritten code calls them
(`tools/bisect_replacements.py` uses that to find a differing function). Instead of a save it can
start a scenario from its file (`'..\maps\Britain.gmp'`, with `--do=@tools/actions_scenario.txt`
to set a game speed), and `--quit` closes the game normally afterwards so its shutdown runs too.
`--menu` loads nothing: the script drives the menus from the first frame, for example into the map
editor (`simcheck.py editor.gmp 2000 --menu --do=@tools/actions_editor.txt`: a new map, the
terrain, tree, bulldoze, region and territory tools, and the editor's setup window with several
of its pages); `tools/actions_menus.txt` first visits the high scores, a new campaign's screen
and the credits, `tools/actions_menus2.txt` the new and saved scenario screens, the LAN screen and
the settings. `--sound` turns the effects and music on (the game's audio session muted), so the
sound code runs too.

Before saving, the harness clears record bytes that the original fills from stack leftovers and
that no code reads (the padding after each name in the cities' building mixes, train padding,
three spare track fields and the cars' unused point; `kUnreadPadding` in `src/harness.cpp`), in
every run alike, and logs how often a path ran where the original reads such a leftover
(`g_unwrittenReads`: the rewrite uses 0 there). Everything else in the save is compared as written.

**Scripted calls**: functions no play-through reaches are called inside a run with real objects
of the loaded save as arguments (`call <addr> <cc> <ret> <args>`: "the 3rd company", "station
id 5", a field of the engine, a record of given bytes; `poke` switches on an option first). The
original run calls the original, the rewrite run the rewrite, and simcheck compares their results
besides the save and the drawing: `tools/actions_calls.txt`, `actions_calls2.txt`,
`actions_windows.txt` (the company, station, train and building windows) and
`actions_dialogs.txt` (dialogs, scenario effects and timed events), `actions_options.txt` (the
options dialog's 13 pages: a modal dialog opened by a call, the following actions run inside
it) and `actions_events.txt` (the scenario editor's rules and condition dialogs).
`tools/autocall.py` generates such calls for every function no game check has run yet (its
object from the name prefix or source file, ids of real objects for parameters named like one),
and `tools/autocall_run.py` runs them in chunks: calls that stop or fault the original are left
out (`out/autocall/skip.txt`), differences go to `out/autocall/findings.txt`, and the coverage
files feed `tools/coverage.py`.

**Generated tests**: `tools/gen_test.py` writes a difftest for functions that need their callees
faked (dialog layout helpers, device code): every function they call is replaced by a recorder
on both sides, and the recorded calls, globals and buffers are compared over random inputs
(specs in `tests/gen_specs/`; the result goes at the end of `tests/test_ui.cpp`).

**Multiplayer**: `python tools/mpcheck.py tools/mp_host.txt tools/mp_client.txt 2000 --client=rewrite`
runs a host and a client on this machine (LAN, 127.0.0.1); their scripts drive the menus with
mouse clicks and the harness's widget dump (`dump`: every window and widget, with captions).
The game's weekly state check (switched off in the shipped game) compares the client with the
host; with the original on one side and the rewrite on the other, any difference shows as a
mismatch. `--host=rewrite` swaps the sides.
`tools/mp_host_play.txt` / `tools/mp_client_play.txt` (3,000 frames) play the game as well: both
players found a company, and the host builds a station in Washington DC, lays track from it,
builds a second station on it, and buys a train that runs between the two. For that the harness
can work in the game world by map cell (`look`, `zoom`, `cell`, `cellclick`, `celldrag`, found
with the camera's own ground pick), log cities and track pieces with their cells (`cities`,
`tracks`), take screenshots of the game window (`shot`, PNGs with `tools/shot.py`), hold keys,
wait for the game to start, and switch off its automatic Enter in dialogs it works itself. All
actions are listed in `tools/simcheck.py`.
Both players also send messages with `Net_Send` (a `call` with a `w...` word buffer): chat with
its backslash commands, the requests the host relays to everyone (bulldoze, electrify, rename,
colours, the stock, bond, share and dividend actions; bankruptcy, merger, dissolving and engine
replacement for company or train id 0, which is never valid), a scenario check the host answers,
and a few host messages. Relayed messages
apply when they arrive, not at a fixed tick, so the scripts only send ones that change nothing a
weekly check compares (same names and colours, an empty cell, money, invalid ids); the original against
itself stays in sync with them, and so do both mixed pairings.

**Coverage**: simcheck records which original functions ran (a one-shot breakpoint on each),
and `build.bat test` does the same for the difftests when `RT3RE_COVERAGE` is set.
`tools/coverage.py` merges those (and the leaf test's table) into `docs/coverage.md`: which
rewritten functions have been run side by side with the original. Every function that has not is
listed there with the reason from `docs/unchecked_reasons.txt`. The run files it merges are kept
in `out/coverage_runs/` (`python tools/coverage.py --difftest=out/coverage_runs/difftest.txt
out/coverage_runs/<run>.txt ...`).

`tools/callcheck.py` compares, per function, what the original's machine code calls with what
the rewrite calls (a `strcmp` where the original calls `stricmp` shows up there), and
`RT3RE_TRACE=<addr>,...` logs every call of those exe functions with their arguments, for
tracking down a difference.

Tests and simcheck run in `%TEMP%\rt3_stock`, a mirror of the game folder without mods
(`tools/stockgame.py`), so they always compare against the unmodified game. The game's data
is shared read-only; what the game writes (settings, logs, saves) stays in the mirror, and
every run starts from the game folder's settings.

A function only counts as done when it has a passing difftest, or, where the function only makes
sense inside a running game (rendering, UI, networking), after a recorded in-game check.
